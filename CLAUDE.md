# Rhino Worktree Launcher

Independent .NET 8 Windows application with one backend and three adapters: native WPF, `rwl` CLI, and stdio MCP.

## Architecture

- `RhinoWorktreeLauncher.Core` owns the schema-v6 app-local project catalog, stable Git worktree identity, read-only repository scanning, canonical solution discovery and builds, remote mirrors, the launch executor and the registration lease it runs, exact loaded-binary verification, the live RWL process inventory, live Rhino instance attribution, diagnostics, and client configuration merging.
- `RhinoWorktreeLauncher` is the native WPF adapter. It binds backend DTOs and invokes backend commands in process. It must not run Git, MSBuild, or Rhino directly.
- `Rwl.Cli` is the script/diagnostic adapter and Claude `SessionStart` hook target.
- `Rwl.Mcp` is a thin newline-delimited JSON-RPC stdio server over the same commands. Each launch tool remains one blocking request. It proves the interactive spawn chain once at startup, so a host that cannot reach the shell fails every launch immediately instead of at the verification timeout, and it ends with the session that started it.
- `Rwl.Bootstrap` is the stable `%LOCALAPPDATA%\RhinoWorktreeLauncher\bootstrap\rwl.exe`. It resolves `current.json` and forwards to the current versioned desktop, CLI, or MCP executable. Two modes are not forwards: `launch-executor`, which the interactive Windows shell resolves and which hands the command to the current CLI, and `registry-probe`, which it answers itself.
- The **launch executor** owns every registry mutation, the Rhino start, verification, and the restore (ADR 0015). It runs in a process the interactive Windows shell starts, because a launcher host can run with its current-user registry writes intercepted, seeing its own writes while the registry Rhino reads never receives them. Adapters are thin clients of it.
- `eng/New-RwlPackage.ps1` is the only installable-payload producer. Source installs, packaged installs, and releases consume its payload shape; the installer never owns a second build or publish implementation.

The backend is a one-off bootstrapper, not a Rhino session monitor. Do not add durable launch operations, reattachment, background observation, or a service.

## Contract invariants

- Project settings belong only in `%LOCALAPPDATA%\RhinoWorktreeLauncher\projects.json`; never require or create repository configuration JSON.
- Catalog schema v6 stores project identity, Git common directory, primary checkout, explicit grants, Rhino version, canonical plug-in project, solution Configuration and Platform, and the desktop launch-mode default. Beside those per-project records it holds one catalog-wide value, the project the desktop opens on. Repositories contain no RWL driver or configuration file.
- The desktop opens on the project the catalog recorded as selected, and on the first by display name when none is recorded or the recorded project is gone. `ProjectCatalog` owns that rule and `ProjectCatalogView.SelectedProject` carries the answer, so no adapter re-derives it. The desktop is its only writer: it records a selection only when the selection actually changes, so reopening the remembered project writes nothing, and removing a project forgets it rather than leaving a dangling id. The CLI and MCP resolve a project from the working directory instead of selecting one, and neither reads nor writes it.
- Schema-v2 catalog data is imported once under the catalog lock and atomically replaced. Ordinary catalog reads never write or prune; invalid registrations remain visible as degraded until explicit removal or re-registration.
- A saved build profile is checked against the primary checkout on every catalog read, cheaply: two existence checks on the saved solution and plug-in project. Only when those fail does the read scan for any remaining Rhino plug-in project. One remaining keeps the project available with a warning to choose it again in Config; none remaining degrades the project, because Config has nothing left to offer. Registration already refuses a repository with no Rhino plug-in project, so the two gates agree.
- Catalog writes re-read while holding the file lock and replace atomically.
- Remote failures are warnings and never hide local worktrees. Remote reads use an RWL-owned mirror and never fetch into a registered repository.
- The selected Git worktree is the single source of truth. Do not create an app-owned source or build tree.
- Config requires an explicit canonical plug-in project when a repository has more than one candidate; discovery must remain available so the UI can present that choice. Never infer project identity from existing `.rhp` outputs.
- Build & Launch runs the selected solution and its Configuration and Platform in the selected worktree. Direct Launch skips the build. Both resolve the selected plug-in project's mapped MSBuild `TargetPath`; never guess, copy, or select an `.rhp` by filename.
- A diagnostic's `Message` is always displayable: short, complete on its own, safe in a one-line status surface. Its optional `Detail` carries the failing tool's own output, bounded, so a surface offers it behind a disclosure instead of choosing between quoting it whole and losing it. The launch log stays the unabridged record. No adapter inlines `Detail` into `Message`, and none repeats what it already streamed.
- A build blocked by another program holding its output file open is its own named failure, `build_output_locked`, detected from MSBuild's `MSB3021` and `MSB3027` identifiers rather than their translated prose. Its message names the held file, names any live Rhino holding a plug-in artifact from that worktree, and stops there. Holders are named with the ADR 0002 attribution query, which reads Rhino and nothing else, so a holder that is not Rhino is reported as unnamed rather than guessed at. Every other failing build is `build_failed`, whose message states how many distinct errors there were and what the first one said. Both carry the build's output as `Detail`. `artifact_prepare_failed` means a prepare step that is not the build, and carries no detail.
- Launch mode belongs to the invoking adapter. The desktop and CLI pass the saved Config default; MCP publishes separate Build & Launch and Launch Existing tools and never inherits the desktop default.
- **No registry mutation may run in a launcher host process (ADR 0015).** Hosts resolve and build; the launch executor owns journal recovery, the lease, the Rhino start, verification, and the restore, and relays progress and one terminal result over a versioned pipe protocol. Nothing depends on a registration an independent process has not confirmed: the seed is written, checked through a separately spawned reader with a per-launch nonce that is removed once confirmed, and only then does Rhino start. A seed nobody else can see ends the launch before Rhino starts. Every failure ends in a named diagnostic code identifying the failing step; a launch never ends in an unnamed timeout, and one queued behind another names the holder of the lock.
- Rhino startup uses a serialized temporary HKCU registration as its only plug-in loading mechanism (ADR 0012, 0014). The lease always clears the current-user key and writes the documented install seed, root `Name` and `FileName` plus the `LoadMode` the displaced registration recorded, which Rhino installs and loads at startup. No seed is written at all when a machine registration already names the selected artifact, because Rhino loads the file from that registration and a seed beside it claims an ID Rhino has already registered; a hand-built complete registration is silently ignored, and there is no redirect shape. Rhino derives a load mode only by instantiating the plug-in, so a seed without one installs as a demand load and an `AtStartup` plug-in never loads at startup (ADR 0014 amendment). The machine hive's recorded mode wins over the current-user one, and a disabled mode is never carried. Never also pass the `.rhp` on Rhino's command line: that asks Rhino to install an ID the overlay has already registered, and Rhino rejects it as an ID already in use. Restore before launch returns; never require elevation.
- One lease owns both hives for one (Rhino version, plug-in ID) pair under one lock and one journal (ADR 0014). The journal holds both hives' pre-state and is written before any mutation; a null current-user entry means the key did not exist, so restoring deletes it, which is what erases a killed launch's install seed. The machine entry is a captured pre-state whether or not the launch displaced it, and a separate flag decides whether the launch's own restore writes that hive (ADR 0015). Every launch restores a pending journal before reading any registration. Reading a registration and displacing it are one decision made once: never re-read a key another component just read for the same decision. A registration counts in either shape, `PlugIn\FileName` or seed-form root `FileName`, in either hive.
- A machine-wide registration for the selected plug-in ID that names a different file always wins over the current-user seed (verified live: HKCU does not shadow HKLM for a duplicate plug-in ID). Where the user granted write access to the machine `Plug-ins` key, the lease displaces that registration and restores it when the launch ends (ADR 0013). Without granted access, launch refuses before Rhino starts and names the registered path, the key, and both remedies; RWL never elevates. A machine registration naming the selected artifact is not a competitor, and the launch writes no current-user seed beside it. An existing current-user registration never blocks a launch: it is captured whole, displaced, and restored.
- The journal outlives the launch's own restore (ADR 0015). Rhino writes the artifact it loaded back into its registration while the launch that started it has already restored and returned, so the executor lingers detached until Rhino exits, compares both hives against the journaled pre-state, restores again if either drifted, and only then deletes the journal. The machine hive's pre-state is captured whether or not the launch displaces it, so that comparison can tell an absent key from an untouched one.
- Process creation is not success. Launch succeeds only after the launched Rhino process holds the selected `.rhp` mapped in its address space (external file-use attribution, ADR 0002; no in-Rhino verifier plug-in, which can never verify its own loading). Critical dependencies are existence-checked beside the plug-in during prepare, not load-gated: lazily-loaded dependencies are legitimately unmapped at startup. Timeout terminates the unverified child.
- **Which live Rhino runs which build is a launcher query, not a consumer's guess.** Concurrent launches legitimately leave several verified Rhino processes running, each a different build, so RWL answers, for every live Rhino process, which `.rhp` files it holds mapped. It is ADR 0002's mechanism asked without an expected path: plug-in agnostic, point-in-time, and read-only, never a session monitor. It is published on all three adapters (`rhino_worktree_attribution`, `rwl rhino instances`, and `rwl doctor` beside the process inventory), and several live Rhino processes are informational there, never a warning. A Rhino this account cannot open for a virtual-memory read is reported as unattributable with the reason, never omitted.
- The launched Rhino carries the launch's identity in its environment, `RWL_LAUNCH_ID` and `RWL_ARTIFACT`, recorded in the launch log, so code running inside Rhino identifies its own launch with one environment read. RWL never reads another process's environment: the process id belonging to a launch is already in that launch's result and log.
- A launch may carry a caller-supplied environment map, injected into the launched Rhino process only — how an in-Rhino automation harness that arms on an environment read is entered through an ordinary launch. `LaunchEnvironment.Describe` in the protocol file is the one definition of a valid map (`RWL_` names reserved, at most 32 variables), applied by the coordinator before any work as `invalid_environment` and re-checked by the executor as `executor_request_invalid`. The launch log and executor log record injected variable names only, never values. The MCP launch tools take the full map; the CLI fallback takes one `--env NAME=VALUE`; the desktop takes none. The field raised the executor protocol to version 2, because an older executor would silently start Rhino without the variables the caller depends on.
- Every launch writes inert JSONL diagnostics under `%LOCALAPPDATA%\RhinoWorktreeLauncher\logs`, recording the host kind, the release, the resolved artifact, the seed values written, every stage transition with its timestamp, and the path of the executor's own log beside it.
- **A stdio server ends with the session that started it.** `rwl-mcp.exe` watches both the standard input its client owns and the process that started it; either one ending stops the host, and a host that has not stopped within the grace does not keep the process alive. The bootstrap owns the same end for the child it forwards to: it closes that child's input, and ends a child that has not exited within the same grace. An in-flight launch is unaffected, because the launch runs in the detached executor, which treats a vanished client as its named disconnect and still restores. A server that outlives its session is unreachable and serves the release it was spawned from, which is why `rwl doctor` reports one.
- `rwl doctor` lists the live RWL processes with their role, the release directory each was resolved from, its start time, and whether the process that started it is still running. Two are findings, both warnings with remediation rather than failures: a session-bound process whose parent is gone, and a process serving a release the installation has replaced. A launch executor and the desktop outlive the process that started them by design and are never called orphaned. Doctor reports; it never ends a process it found.
- Verification builds may compile the solution, but only the canonical package producer defines distributable binaries.
- Claude install/remove owns only the `rhino-worktree-launcher` MCP entry and the RWL `session-context` hook. Preserve all unrelated settings and integrations.

## Build and verify

```powershell
dotnet build RhinoWorktreeLauncher.slnx -c Debug
dotnet test tests/RhinoWorktreeLauncher.Tests/RhinoWorktreeLauncher.Tests.csproj
dotnet test tests/RhinoWorktreeLauncher.UiTests/RhinoWorktreeLauncher.UiTests.csproj
```

`UiTests` is the seam for the WPF surface: it asserts against the XAML documents and the built desktop output, so any change to the native surface is verified there rather than by eye alone.

The WPF design remains the completed fixed 720 x 1000 native surface. Preserve its theme, typography, scrollbar gutter, shared corner-radius tokens, and current interaction details while changing backend behavior. `Config` is project-specific; global `Settings` owns MCP setup.
