# WPF adapter

This project owns only the native Windows presentation surface. `MainWindow` binds backend DTOs, invokes `LauncherBackend` commands, displays progress, and presents terminal diagnostics. It must not duplicate Git scanning, canonical solution validation, build execution, Rhino launch, or launch-verification logic from `RhinoWorktreeLauncher.Core`.

The fixed 720 x 1000 main interface follows `AppsUseLightTheme`, embeds the approved IBM Plex Sans and Geist Mono static fonts, and uses Ideal metrics, Fixed hinting, and ClearType. Keep the DWM-visible frame sizing, shared corner-radius tokens, project identity block (fixed-width drop-down selector above, quote-ruled repository path centred in the gap below), Refresh progress control, and Add project ghost-button behavior. One inset separates content from every window edge: `ContentArea` states it for the left, top and right, and `FooterBar`, as the last row, states it again for the bottom. No region inside them re-states an edge inset of its own.

The status report is `PanelHintText` inside `PanelHintBanner`, a banner floating over the bottom of the worktree list rather than a column in the panel header, where variable-length messages competed with three permanent captions. It carries every hint the surface has: refresh stages, one line per MSBuild progress update, the launch verdict, and exception text. `ShowHint` is the only writer, so the banner is absent whenever the hint is empty, which is the steady state after a clean scan.

Launch progress reports there too. `LaunchProgressFill` is a rectangle, so its leading edge reads as the reading, and `PanelHintBannerClip` rounds it to the banner's inner corner at a size that follows the panel. It sweeps the banner's own width, which follows the panel, so the sweep measures `PanelHintBanner` rather than trusting a constant, and `BeginLaunchProgress` lays the banner out before the first stage animates because a collapsed banner has no width to cross. A launch holds the banner open even before it has anything to say. The launch button is a button: it shows its mode, and it is disabled while a launch runs rather than lit and unclickable.

The scrollbar floats over the rows' own padding instead of taking a gutter beside them. A gutter that appears with the scrollbar moves every row sideways on the one occasion the list is long enough to scroll, and the BEHIND and AHEAD captions above the rows cannot follow it.

A launch failure opens `LaunchFailureDialog`, not `MessageBox`. The diagnostic's message leads, its `Detail` waits behind the `DetailsToggle` disclosure in a scrolling monospaced panel, and the launch log path sits in the footer. A diagnostic with no detail shows no disclosure. `MessageBox` remains correct for the short integration failures in `Settings`, which have nothing to expand.

`Config` is the project-specific surface for the canonical Rhino plug-in project, solution, Configuration, Platform, launch mode, and project grants. When multiple plug-in projects exist, keep Config available and require the user to select one there. Do not ask the user to select a built `.rhp`; MSBuild `TargetPath` derives that artifact from the saved project and solution configuration. `Settings` is the global surface for MCP setup. The footer contains Settings, Open folder, and the launch action. Do not restore the retired bottom-left selected-worktree indicator or a second MCP button.

Every project, solution, and configuration selector uses the shared `Themes/DropdownStyles.xaml` component: 38px value surface, 9px radius, explicit caret, visible focus ring, matched rounded popup, 32px menu rows, and the selected-worktree texture plus accent check. Keep value templates explicit, and give item containers accessible automation names, so records never render through diagnostic `ToString()` output visually or to assistive technology. Show dependent selectors disabled with directional placeholder text until options exist.

Launch is explicit through the button or Enter key. Double-click does not launch. The button label follows the selected project's Build & Launch or Direct Launch mode and waits for loaded-binary verification; it must never infer success from `Process.Start`.
